# cyberia-content

The Cyberia content: the foundation, the instances, the sagas, the semantic generator and the
versioned content artifact the engine consumes.

This repository creates content. The engine imports, materializes, releases and deploys it.

```
cyberia-content ──validate──► build ──► dist/ (the content artifact: data and its manifest)
                                              │
            engine: this checkout (CYBERIA_CONTENT_ROOT) or a packed copy of it
                                              │
                cyberia instance --import · content import · content-release
```

## Layout

| Path                      | Holds                                                                                  |
| ------------------------- | -------------------------------------------------------------------------------------- |
| `src/content/foundation/` | The functional blueprint: world, environment, items, characters, maps, quests, actions |
| `src/content/instances/`  | Instance backups, one directory per instance code, as the engine exports it            |
| `src/content/sagas/`      | Saga packages, one file per saga code                                                  |
| `src/schema/`             | The definition schema and the runtime contract (generated by the engine)               |
| `src/validation/`         | Content rules and the canonical JSON form                                              |
| `src/compiler.js`         | Definitions to runtime documents: one list per document family                         |
| `src/generator/`          | Semantic generation: prompts, stages, the saga package, the Gemini client              |
| `src/packaging/`          | The artifact: build, manifest and digests                                              |

## CLI

```bash
npm install
node bin/cyberia-content.js <command>
```

| Command            | Does                                                                            |
| ------------------ | ------------------------------------------------------------------------------- |
| `validate [--fix]` | Validate canonical form, foundation, sagas and instances; `--fix` rewrites form |
| `saga generate`    | Compose a saga with Google Gemini and write its package                         |
| `build`            | Write `dist/` from the committed content                                        |
| `pack`             | Build and pack `artifacts/cyberia-content-<version>.tgz`                        |

`--env-file <path>` reads the environment from a file. `./.env` is read when it exists.

## The foundation

The foundation defines what exists and how it functions. Studio adds only how it looks (render)
and where it is (placement).

A definition id is `<kind>.<slug>`, for example `biome.violet-strata`. One JSON file holds one
definition, at `<category>/<id>.json`. Every definition has a `name`, a `description` and a `role`.

| Kinds                                                                                                                   | Define                                                                  |
| ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `region`, `biome`, `faction`, `origin`, `material`                                                                      | The world. Only the foundation defines them                             |
| `floor`, `tree`, `vegetation`, `rock`, `prop`, `structure`, `ruin`, `portal`                                            | Environment: each one is an Object Layer item and an entity             |
| `weapon`, `armor`, `skin`, `projectile`, `currency`, `resource`, `consumable`, `relic`, `technology`, `implant`, `tool` | Carried items                                                           |
| `character`                                                                                                             | Loadout, carried items, the spawned `entity` and a `greeting`           |
| `ability`, `effect`                                                                                                     | What items do: a runtime skill handler and its effects                  |
| `map`                                                                                                                   | A place of one `biome`, and its `composition`: each entity and how many |
| `quest`                                                                                                                 | Provider, steps, objectives, rewards and `talk`                         |
| `action`                                                                                                                | What a provider offers: shop, recipes and storage                       |

An item or environment definition carries an `objectLayer` block: the item type, the `activable`
flag and the stats. Its item label is its slug. Its `artBrief` tells an artist what to draw. It holds
no pixels, frames, atlases or CIDs.

A biome carries a `palette`: `#rrggbb` colors by role (`base`, `shadow`, `highlight`, `outline`,
and optionally `accent` and `special`). The Studio paints with it; it is guidance, never render.

A map composes entities its biome holds. The compiled map holds none: Studio places each one and
tracks the composition against the context index. A quest provider and each talk target stand
behind an action of the same set.

`foundation.json` holds the `schemaVersion` of the definition format and the `baseline`: the
definition each runtime entity type resolves against when a world authors none.

## The compiler

`src/compiler.js` turns definitions into runtime documents, one list per family, in import order:

| Family                 | Documents                                                                 |
| ---------------------- | ------------------------------------------------------------------------- |
| `object-layers`        | One Object Layer item per labeled definition, without render              |
| `entity-type-defaults` | One per entity definition: live, dead, drop and inventory items, behavior |
| `skills`               | One per item whose abilities name a runtime handler                       |
| `maps`                 | One per map: code, name, description and biome tags; no entities          |
| `quests`               | Steps, objectives and rewards by item label; source map and cell null     |
| `dialogues`            | Item flavor text, character greetings and quest talk                      |
| `actions`              | Shop, recipes, storage and quest talk codes; source map and cell null     |

The same compiler compiles the foundation and each saga. It also derives the context index the
Studio reads: every definition of the foundation and the sagas, its source, the item label and the
map entity it answers to, and every reference in both directions with the field that makes it.

## Semantic generation

The generator composes a saga over the foundation. Gemini reuses foundation definitions and adds
only what the saga lacks, in the definition model of the foundation.

```
theme  (from --prompt, or synthesized from the lore)
   │
   ▼
Google Gemini, six bounded stages, each one returning definitions
   │   1 composition → saga identity, the foundation ids it uses, new definitions
   │   2 maps        → maps of foundation biomes, and what each one composes
   │   3 quests      → quests over characters and items
   │   4 dialogues   → greetings of new characters and the talk of quests
   │   5 actions     → what each quest provider and talk target offers
   │   6 abilities   → abilities of new items, reused or defined
   ▼
normalize → validate → src/content/sagas/<saga-code>.json
```

The composition stage reads a compact index of the foundation. Each later stage reads the full
definitions of what the saga uses. The model follows these rules, and normalization enforces them:

- Reuse a foundation definition by its exact id. Never define a duplicate.
- Never define a region, biome, faction, origin or material.
- Use only the skill handlers of the runtime contract.
- Write no coordinates, cells, grids, portal endpoints, pixels, frames, atlases or CIDs.

An invalid package is written for a human to fix. The command then fails with its findings.

```bash
# A lore-grounded saga. The world foundation is the lore unless --lore-path names a document.
node bin/cyberia-content.js saga generate

# A given theme, validated but not written
node bin/cyberia-content.js saga generate --prompt "A relay keeper in the ash wastes" --dry-run
```

`GEMINI_API_KEY` must be in the environment. Steer a synthesized theme with `--space-context`
(`physical`, `mixed`, `hyperspace`), `--tone` (`adventure`, `politics`, `tragic`, `comedy`),
`--faction-context` (foundation confederations that drive the saga, for example `nova,zenith`),
`--character-context` (name pools) and `--cultural-exposure` (`cosmopolitan`, `local`).

### The saga package

| Field               | Holds                                                                  |
| ------------------- | ---------------------------------------------------------------------- |
| `schemaVersion`     | Version of the package format                                          |
| `foundationVersion` | The content version the saga was composed against                      |
| `saga`              | `code`, `name`, `description`                                          |
| `references`        | Every foundation id the definitions name                               |
| `definitions`       | The new definitions, maps, quests and actions, in the foundation model |

The build compiles a package with the compiler of the foundation. The saga adds its own documents
of every family, its `CyberiaSaga` record and the shell of its instance.

## The runtime contract

`src/schema/runtime-contract.json` holds the runtime vocabulary content uses: item types, entity
types, stat bounds, skill handlers, quest step types and the item dialogue prefix. The engine owns
that vocabulary and generates the file with `node bin/cyberia stat-contract`. Never edit it.

## The artifact

The artifact is data: `dist/` and its manifest. It holds no code; the consumer verifies it.

| Path                              | Holds                                                 |
| --------------------------------- | ----------------------------------------------------- |
| `dist/manifest.json`              | Identity and the digest of every file                 |
| `dist/context.json`               | The context index of the Studio                       |
| `dist/foundation/<family>.json`   | The compiled foundation, one file per document family |
| `dist/foundation/baseline.json`   | The entity-type defaults a world resolves against     |
| `dist/sagas/<code>/<family>.json` | Each compiled saga, one file per document family      |
| `dist/sagas/<code>/saga.json`     | Its `CyberiaSaga` record                              |
| `dist/sagas/<code>/instance.json` | The shell of its instance                             |
| `dist/instances/<code>/`          | Each instance backup                                  |

The manifest names `repository`, `contentVersion`, `sourceRevision`, `schemaVersion`,
`contentDigest`, `build`, `instances`, `sagas` and `files`. The content digest is the sha256 of one
`<path> <sha256>` line per file, in path order. The same commit always builds the same bytes.

The engine reads the artifact of this checkout in development: run `build` after each commit.
`pack` writes the same artifact as `artifacts/cyberia-content-<version>.tgz`; the engine reads an
extracted copy the same way. A registry, an OCI image or a release asset can carry that tarball
later without a change to the artifact.

## Release

1. Change content, run `validate`, and commit. The build refuses uncommitted content.
2. Increment `version` in `package.json` and commit. A released version never changes.
3. Run `build`. The engine reads the new artifact from this checkout.
4. In the engine, `cyberia instance --publish-build` records the artifact in the deployment
   `content-lock.json`. The image build checks out that source revision and builds it again.
